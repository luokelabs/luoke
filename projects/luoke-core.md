# 螺壳 luoke-core

- 仓库：[`luoke-core/`](../luoke-core)；设计：`luoke-core/docs/DESIGN.md`，v1 范围和接口细节：`luoke-core/docs/V1.md`
- 本页由 luoke-core 的会话维护。

## 是什么

螺壳工具共用的本地 AI 主控：一个菜单栏程序，管本机所有模型推理（加载、内存、功耗、排队），按实验室发布的配方决定用什么模型做什么任务；配方里的每个选择都有实测证据。它同时是螺壳工具的安装器和更新器。模型的推理和权重归主控（顶层 ADR 0014、0018）。

## 对外提供

**给配件（螺壳的工具）**
- **任务层**：本账户的 Unix socket（`~/Library/Application Support/luoke-core/run/hub.sock`），接入参考 `luoke_core/client.py`。
  - 生成：OpenAI 兼容、一律流式，按 `X-Luoke-Priority` 分"用户在等"和"后台"。
  - 打分、联想、续写：专用模型直连，按配件保留前缀快照。专用模型的工作进程空闲 10 分钟停、下次用到再起（重起期间答 `not_ready`，`retry_after` 2 秒）；内存不够时不起（`retry_after` 30 秒）。
  - 嵌入：`POST /tasks/<任务>/v1/embed`，后台批和用户在等的查询走专用模型自己的通道。
  - `GET /tasks`：本档能用的任务、参数、状态，以及只用来显示的 `model_name`（`combo` 不解析）；顶层的 `luoke_mem` 给出主控里那份记忆库的位置。
  - 预热、常驻声明、退出通知；被挡回时有统一的原因码和 `retry_after` / `retry_after_ms`（V1 §2）。
- **配件接入契约**（DESIGN §11、V1 §8）：打包与身份、用模型的方式、评测集、数据与升级、界面与安全。
- **空闲任务**：配件在清单 `jobs` 里登记"空闲时跑"的命令，主控在安静时刻拉起、用户回来时让它收尾（V1 §8）。
- **主控自带的 Python 可以借**：`螺壳.app/Contents/Resources/python/bin/python3`（改名前装的是 `螺壳主控.app`；装在 `/Applications` 或 `~/Applications`，ADR 0012）（python-build-standalone 3.12，同一个 Team 签名）；契约 1 内路径和 bundle id `ai.luoke.core` 不变，换大版本前先写进这里并通知用它的配件（V1 §8）。
- **配件用主控里那份 luoke_mem**：`GET /tasks` 顶层 `"luoke_mem": {"path", "version", "python"}` 给出 site-packages 的位置和主控自带的解释器（不带 Python 的工具用它跑 `-m luoke_mem`）；工具每次新起进程时问一次、插到 `sys.path` 最前面再 import，主控不在就用自带的兜底那份（兜底那份不比钉住的新）。
- **`GET /accessories`**：装了哪些配件及其清单里的公开字段（含 `capabilities`）。
- **装之前的介绍**（顶层 ADR 0014 的 10-27 修订）：发布流水线把配件清单 `capabilities.listing` 的 `tagline`、`category` 和 `capabilities.permissions` 的说明（`id`、`kind`、`title`、`facts`、`without`）抄进发布清单该项的 `listing`；大小和能在哪档用由主控出，配件自己写的不抄。
- **打包脚本** `tools/package_python_app.py`：配件清单 + 包目录 → 自带 Python 的 .app（V1 §8）。

**记忆（luoke-mem）打在主控里**
- 主控 .app 自带 luoke-mem 的代码和清单（`Contents/Resources/memory/luoke-accessory.json`），配件标识仍是 `luoke-mem`；它的任务、空闲任务、`forget-tool` 都用主控自带的 Python 跑。主控进程本身不读记忆。
- 打开记忆界面：`open luoke://memory`；跳到某一条 `luoke://memory?note=<编号>`；打开到「最近记下的」`luoke://memory?view=recent`。
- 判断记忆在不在：Swift 看 `luoke://memory` 有没有应用能打开；Python 看主控 .app 里的那份清单在不在。
- 主控升级、退出前请主控 Python 跑着的 `-m luoke_mem` 进程退出；luoke_mem 收到 SIGTERM 要干净退出。

**给用户**
- 安装、升级（新的安装器原地升级，旧版留作回退；菜单「检查更新…」按渠道查新版；升级只往新换、不往回降）、配件回到上一版（菜单「配件回到上一版…」，按那一版当时的验证认它）、装完输入法引导添加输入源、卸载（只删配件清单里和它自己的标识绑定的数据位置，记忆文件永远不删；可选从记忆里忘掉它写的东西）。
- 首次运行：按清单下载引擎包和本档模型，先复用本机已有的同名模型（逐文件核哈希、只读克隆）；大内存机器可选「省空间」。
- **给高级用户的本机端点**（顶层 ADR 0014 修订）：设置 → 高级，默认关。OpenAI 兼容的 `/v1/models`、`/v1/chat/completions`，只听 127.0.0.1；模型是主控这一档的底座和用户自己登记的本机模型（`user/<名字>`）。命令行 `luoke launch pi` 一键配好 pi。给用户自己的工具用，配件照旧走任务层（V1 §2b）。

**配方与评测**
- 配方：模型清单、引擎包、各档底座、任务表与任务参数、已验证版本、依据（DESIGN §3）。
- 发布前评测：每个任务在各硬件档上按评测集打分；哪一档开着由支持台账定——连过 3 遍才开，失败一遍就关（顶层 ADR 0017，V1 §10b）。

## 依赖

- 推理引擎：钉住版本、不改代码的 oMLX，打成引擎包，由实验室重签公证（ADR 0001）。
- 模型由实验室量化、托管在 ModelScope 和 Hugging Face；安装包和引擎包发在 GitHub 的 luoke-releases，gitlab.com 上有同名镜像，连不上 GitHub 时螺壳查更新、下载都改走镜像（beta1.1 起）。
- 记忆：luoke-mem（打进主控的那份按发布钉住的提交）。

## 使用方

- luoke-mail：后台批量分拣和其他邮件任务、单次调用。
- luoke-ime：重排打分、联想、续写；个人化组件借主控的 Python。
- luoke-mem：归纳任务（typing、topics），空闲任务 learn。
- luoke-agent：常驻配件，对话和简报任务，`GET /accessories`。
- digup：嵌入。

## 第三方接入：主控这部分（[luoke#1](https://github.com/luokelabs/luoke/issues/1)）

给顶层扩展层 ADR 的输入，2026-11-01 按代码核过。"现状"是事实；"建议"是主控的看法，没定，分工和约定由顶层定。

**现在的前提**：配件都是我们自己的，所以 DESIGN §10 明写配件标识"只用于识别，不是安全措施"，本机组件之间不设限（顶层 ADR 0013）。第三方进来后这条前提不成立，下面几处都从这里来。

### 1. 任务、评测、配方、开发调试

现状：
- 任务只存在于配方的任务表，任务名的前缀必须是配件标识；配方随主控发布，配方外的任务一律不用，没有逃生门（ADR 0003）。
- 配件版本要精确落在配方的已验证版本里，主控才接它的请求；哪怕只改提示词也要重评（DESIGN §7）。
- 评测集由配件出、实验室跑。现在的跑法是 `tools/release_evals.json` 里的一条命令：在出版机上运行配件自带的评测程序。

走不通：
- **第三方发一版要等一版主控**：配方的独立通道排在 v1.x，没做。
- **第三方的评测程序不能在出版机上跑**：它是任意代码，那台机器有签名和公证材料。
- **评测量跟着配件数涨**：每个版本、每个任务在各档都要评，开档要连过 3 遍。

建议：
- 第三方只交数据形式的评测集（录好的请求、判分规则、及格线），由主控的评测框架跑；要自带评测程序的，只能在没有签名材料的隔离环境跑。
- 分两种任务：**专属任务**照现有规则，实验室背书，名额少；**社区通用任务**由配方开少数几个，实验室只验模型和参数，不背书业务质量，界面写明"未经实验室验证"，只走后台、有配额。配方仍然封闭，但"没有评测集不进配方"对通用任务的业务质量放松了，这一点要顶层拍板。
- 配方独立通道（含签名）是第三方节奏的前提，要提前排。

开发调试：
- 现成的是实验室主控：`tools/dev_hub.sh` 起 `--lab` 实例，不核版本、socket 独立，配件设 `LUOKE_HUB_SOCKET` 改连它，`LUOKE_ACCESSORY_DIR` 指向配件目录，任务写进本地配方。这些都在公开的树里，第三方不用进配方就能调。
- 缺的：脚本写死了从 `~/.omlx/models` 链模型、要 oMLX，换薄引擎（顶层 ADR 0020）时要改；没有写给外部开发者的说明。
- 本机放行（`tools/local_allow.py`）帮不上：只在内部版生效，只放行配方里已有配件的新版本，还要我们的签名。
- 建议：调试只走实验室主控，把它做成外部能用的一条命令加一页说明；正式主控不开开发者模式（ADR 0003）。

### 2. 签名、Team ID、撤下

现状：
- Team ID 是写死的常量（`luoke_core/download.py`、`Updater.swift`），装之前核 codesign、Team ID、公证票据，别家签的包主控不装。
- 只有安装时核。运行时按 `*.app` 读清单，不核签名；请求头里的配件标识是自报的，同账户的进程都能连 socket，能冒充任何配件。
- **主控拉起清单 `jobs` 里的空闲任务时不核签名和版本**（`luoke_core/jobs.py`）：放进 `~/Applications` 的 .app 只要带合格的清单，安静时刻就会被拉起。没验证的版本用不了模型，但进程起来了。现在都是自家配件，不算事故；开放第三方前要改成只拉配方认的配件。
- **`revoked` 还没做**：DESIGN §3 写了撤回清单、V1 §4 列为预留，但代码、发布流水线、配方里都没有这个字段；`min_hub_version` 和配方签名同样只在文档里。现在撤一个配件只能发新版主控，用户升级后才生效。

建议：
- 第三方用自己的 Team ID 签名公证，不用实验室的：我们的 Developer ID 签了就等于替它背书，每一版都要经我们的证书。配方里按配件登记 `team_id` 和 `bundle_id`，主控按配方核，取代写死的常量。
- 运行时认人：用 `LOCAL_PEERPID` 取对端进程，核路径和 Team ID，再和配方比；主控认菜单栏本体已经这么做（`peer_is_hub_app`）。限制：借主控 Python 的进程查出来都是主控的身份，这类只能靠下面"由主控拉起"来认。
- 撤回单独做一条通道，随检查更新取，和主控版本无关，先要有签名，否则改了清单就能让别人的配件停摆。范围按配件加版本、或按 Team ID。动作是拒绝模型任务、停空闲任务和常驻、告诉用户，不删数据。
- 撤回只管得到主控的服务：第三方的 .app 自己还能运行，要彻底停只能靠苹果吊销。这是用户授权时要照实说的。

### 3. 轻量扩展（清单、提示词、卡片加一个沙盒进程）

能直接用的：清单里的 `capabilities` 主控原样保存（卡片归 agent 解释）；空闲任务的调度；任务层；装之前的 `listing` 介绍；提示词文件的格式（顶层 ADR 0019）；输入法的先例：引擎在 Seatbelt 沙盒里，经标准输入输出说 JSON 行。

走不通，要主控新做的：
- **扩展不是 .app**：扫描、安装、卸载都认 `*.app` 和 `type`（`app`、`component`、`input-method`）。要新类型 `extension`、固定目录、自己的安装和卸载；不是签名包，身份和完整性靠配方里的内容哈希。
- **谁起进程**：空闲任务用配件自带的 Python 或 `Contents/MacOS/` 里的程序，不进沙盒，环境里是真实的 HOME。扩展要由主控在沙盒里拉起，借主控的 Python，只放行它自己的数据目录。
- **扩展的通信都经主控转发**（和 luoke-agent 商定，2026-11-01）：扩展不开 socket，也不连 socket，只经标准输入输出和主控说话。Seatbelt 本身能按路径放行 unix socket（实测过，监听和连接都可以），不放行是输入法的策略；选转发是为了认人和限额，不是因为技术上做不到：进程是主控拉起的，主控知道它是谁，不用信请求头，配额也按它算。
  - 去任务层：主控按扩展的身份代发。
  - 和 agent：主控在自己的 socket 上给 agent 一个按配件区分的入口，工具协议的 JSON-RPC 原样转，不解释内容，`_meta` 不动，写入调用能等 5 分钟。主控按 JSON-RPC 的 `id` 转，不排队，并发由扩展自己定。进程没起时答"工具没在运行"，什么时候拉起由主控定。只有 agent 能用这个入口。
  - 主控重启或升级时扩展的进程会没，转到一半的写入结果不明，agent 要按"不知道成没成"处理。
- **认人按形态分**（同上）：扩展由主控拉起、按配方内容哈希认，agent 只认主控给的身份，不核扩展的签名。普通 .app 由 agent 按第 2 节的做法核路径和 Team ID，和 `GET /accessories` 给的比。agent 借主控的 Python，按签名查不出它；主控亲自拉起 agent 之后，按对端 PID 加进程启动时间认"主控拉起的 luoke-agent"，这是转发入口核调用方的办法。现在 agent 还不是主控拉起的，要等它随螺壳装（luoke-agent 的注册页）。审过的 .app 同账户里仍能冒充 agent，这个缺口写明，不作为开放前提。
- **提示词谁拼**：提示词和业务逻辑归工具（ARCHITECTURE §1），主控不拼。扩展由自己的进程拼。完全没有进程的纯声明式扩展这一版不支持：主控和 agent 都不解释、不拼提示词，要报事或出卡片就得有进程。
- **改提示词就要重评**：对轻量扩展不现实，这类扩展只能走社区通用任务。
- **没有按配件的限额**：请求等级是配件自报的。扩展一律按后台算，"用户在等"只给用户当场触发的，并且限额。这要在派发里加。
- **记忆只有在沙盒里才挡得住**：`memory` 字段只是声明，`GET /tasks` 给得出路径，沙盒外的进程能直接读 `~/.luoke/mem.db`。"第三方碰记忆要另外同意"（顶层 ADR 0013）只对沙盒里的第三方成立，所以第三方代码默认走扩展，普通 .app 形态只给审过的。沙盒里也不宜放行整个库文件，要一个按范围读写的接口，归 luoke-mem。
- **审过的 .app 和 ADR 0013 有冲突，要顶层定**：ADR 0013 写的是第三方代码跑在沙盒里，审过的 .app 不进沙盒就是例外。要么承认这个例外，要么要求它用 App Sandbox，那样 agent 连它、它连主控都要重新设计路径（socket 放容器里，还要留意路径 104 字节的上限）。

建议的顺序（都不进 beta1 和 11-02 的测试）：只拉配方认的配件 → `revoked` 和配方通道 → 运行时认人 → `extension` 类型和转发。

## 对别的项目的需求

- 每个工具在自己的注册页写清要主控提供哪些任务、调用方式（生成、打分、嵌入）、延迟要求；每个任务交评测集，没有评测集的任务不进配方；随模型变化的数值（门槛、上限、是否思考等）写进配方，不写死在工具里（DESIGN §3、§7、§11）。
- 工具不注册自己的登录项（由系统拉起的配件，例如输入法，是例外），不点名模型，不提供选模型的界面；安装路径由配件类型决定，发布后不变（DESIGN §11）。
- 后台请求按硬件档限制输入长度、配件分段提交；被 `busy` / `paused` 挡回时按 `retry_after`（有 `retry_after_ms` 就按它）重试，主控不排队（DESIGN §6）。
- 配件的代码改了、要换装的，同时升清单里的版本号：主控按版本号判断要不要升级。
- **主控改名「螺壳」（主人 10-23 定，PR luoke-core#26 的提案）**：internal-1024 起更新程序和安装器认「螺壳.app」和「螺壳主控.app」两个名字，internal-1024-2 起主控叫 `螺壳.app`，internal-1025-3 起装在 `/Applications`（`~/Applications` 里的也认，luoke-core ADR 0012）。bundle id `ai.luoke.core`、数据目录 `~/Library/Application Support/luoke-core`、socket、命令 `luoke` 都不变。配件里写死了主控位置的，要在 internal-1026 之前改成两个名字都认：最好按 bundle id 找（Swift：`NSWorkspace.shared.urlForApplication(withBundleIdentifier: "ai.luoke.core")`），Python 先试 `螺壳.app` 再试 `螺壳主控.app`。已接：luoke-mail 0.17.17（c5a4379）、luoke-ime 0.1.14（9dcbc8b），都是两个名字都认。给用户看的文字里的「螺壳主控」随各自的版本改成「螺壳」。
