# 0022 除输入法外的应用都收进螺壳.app

状态：已定（2026-11-05，主人在早会定）。怎么合、什么时候合还没定，见文末。

## 背景

ARCHITECTURE §2 原来写的是「每个工具一个 app，入口只有一个」（主人 2026-10-13 确认），理由有三条：输入法必须是单独的包；系统权限按 app 授权；各自出版本、各自评测。同一条也留了口子：「以后如果出现很多轻量的场景，不一定每个都做成新 app，等第三、四个场景出现时再定要不要有『扩展』这一层。」

到 11-04，记忆和 agent 的核心、主窗口已经在螺壳.app 里；邮件助手、螺壳搜索、螺壳扫描各自一个 .app，由螺壳装进 `~/Applications`；输入法装进 `~/Library/Input Methods`。主窗口的侧栏列出全部应用，经工具协议的 socket 连它们。

原来的三条理由，到这时已经变了：

- **系统权限**：完全磁盘访问已经改成授权给螺壳本身（ADR 0021），扫描、搜索复用这一份。
- **各自出版本、各自评测**：配方按任务名和版本认，和在不在同一个包里无关。「单独升级」不一定要单独的 .app。
- **只有输入法**必须单独成包：它要放在 `Input Methods` 里，由系统的输入法框架加载。

邮件助手会话核过：真正绑在邮件助手.app 上的只有通知身份，收进来以后用户要重新允许一次通知。登录项 0.11 起就没有了；本机网页、钥匙串里的授权码、数据目录都和形态无关。Python 可以改用螺壳自带的；agent socket 的对端核对也会更简单（luoke-ops#85）。

## 决定

- **除了输入法，其他 `luoke-` 应用都合并到螺壳.app**：邮件助手、螺壳搜索、螺壳扫描，以及以后的新应用。记忆和 agent 已经在里面。
- **输入法照旧单独一个包**，装在 `~/Library/Input Methods`，由螺壳安装和升级。
- ARCHITECTURE §2「每个工具一个 app」这一条，按本 ADR 改写。

## 还没定的（luoke-ops#87）

- **怎么打包、怎么按组件单独升级**：由 luoke-core 定。「按组件单独升级」是早会议题的建议，主人的回复没有逐字提到，要确认。和组件版本号、构建号的提案（luoke-ops#83）一起看。
- **时间**：跟不跟 beta 2，由 johnz 定。
- **各组件的硬约束**：
  - 螺壳扫描和螺壳搜索有没有别的，请负责人核；搜索要常驻建索引。
  - agent 在主窗口崩溃修好（luoke-ops#84）之后，还有没有要跟着改的。
- **扩展层**：社区应用、第三方怎么接，和 luoke 自己的 task 协议一起定（luoke-ops#67、#88）；本 ADR 只管我们自己的应用。

## 后果

- 「一个工具、一个身份」不变：在同一个包里，对主控和记忆来说，每个工具仍是一个配件、一个身份。工具之间不互相调用，照 ADR 0014。
- 通知要改由螺壳发出，从单独的 .app 换过来的用户要重新允许一次。
- 各组件的打包脚本、配件清单、出版流水线、「应用」窗口、卸载，都要跟着改；具体由各负责人在 luoke-ops#87 定。

## 修订（2026-11-05，整体升级）

主人 11-05 确认「整体升级就行」：**收进来的应用跟螺壳一起升级，不做按组件单独升级**。哪个应用有新版，就出一版新螺壳，用户整个换。输入法、引擎、模型照旧单独下载、单独换。

luoke-core 的打包方案在 luoke-ops#87 等 johnz 定。方案的大意：

- Python 的应用放进 `Contents/Resources`，用螺壳的 Python；
- Swift 的应用编成 `Contents/Helpers` 里的辅助程序，由螺壳拉起；
- 通知由主控代发；
- 老用户第一次起新螺壳时，旧的 .app 挪进废纸篓，数据目录不动。

理由是签名只有一份，在签好名的 .app 里不能单换一个目录；用户也只要升一次。时间还是由 johnz 定。
