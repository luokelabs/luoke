# 0027 产品线和发版品控分开：品控按版本做，不按 PR 做

状态：已定（2026-11-11，主人定）。

## 背景

此前螺壳的组件按人分：有的组件归主人这边，有的归团队成员；研发上的取舍、PR 的放行多半要跨机器来回。组件越收越多进螺壳.app 以后，一个产品改动常常同时碰到几个人负责的组件，每一步都要等另一边回应，协作变乱，也拖慢了迭代。

## 决定

- **产品线归一处**：螺壳 app 的全部产品代码（主控的产品部分、agent、探头、搜索、输入法、邮件、记忆）由主人这边迭代。产品上的事（做什么、界面、取舍、哪个改动进哪一版）由主人定。
- **发版和品控单独一条线**：出版流水线、截版和发布、公开同步、评测程序和评测集、配方的验证、配件发布的 CI 由 johnz、Keith 负责。这一版能不能发，由他们看评测和 CI 的结果定。
- **品控按版本做，不按 PR 做**：产品仓库的 PR 主人同意就能合，不再要求作者以外的人逐个审。品控在发版时把关：没过就报哪一项没过、卡在哪个提交，只报事实；怎么修由产品这边定。
- **提示词改动**（ADR 0019）：照旧走 PR、附评测结果，安全相关的附改动前后三档的逐题对比；不再要求另一位成员审，能不能随这一版发由品控看评测定。
- **科研单独做**：推理引擎（ADR 0020）、专用的垂直小模型由 johnz、Keith 做实验，结论报给主人；要不要用进产品由主人定。
- **品牌和外部趋势**：Jason 看外面 Local AI 的讨论趋势，和主人一起做品牌；官网、文案、社区照旧（ADR 0017）。
- 两条线之间只留三样往来：产品这边交版本，品控回结果，科研和趋势报进展。

## 取舍

- 逐个 PR 的审核能更早发现问题，但每个改动都要等人；按版本把关发现得晚一些，靠评测和 CI 的覆盖面补。评测和 CI 核什么由品控这条线定，并随发现的问题补。
- 主控仓库里既有产品代码，也有出版和评测的部分。仓库归产品线，出版和评测的目录由品控这条线负责；产品会话不改这部分，要改就提 issue。

## 影响

- 取代此前各处「研发决策由 johnz 判断」「共用仓库的 PR 要另一个人审」的写法；ADR 0019 里「提示词 PR 要一位成员审」的要求按本条改。
- 往公开处发（测试版、正式版、公开同步）照旧每个公开版开始前由主人同意一次（ADR 0017）。
- 配件单独发版由发布流程的 CI 把关，另记一条（0026，待定稿）。

## 2026-11-11 修订（同日补充）：安全和 CI 归发版品控一侧

主人补充：产品研发的推进在产品线一侧，发布流程、安全、CI 仍归发版品控一侧。

- 各产品仓库的 CI 配置归发版品控一侧，由他们改、他们同意合。
- 安全相关的改动（安全审查提出的修复、本机数据加密、签名和授权的核对）由发版品控一侧写、他们同意合；这是「发版品控一侧不再往产品仓库合产品改动」的例外。
- 产品会话不做这两类，要改就提 issue。

## 2026-11-12 修订：应用界面规范归产品线

主人定：应用界面规范收到产品线。

- 应用里所有面向用户的界面（桌面小精灵、首页、各应用页面、设置、安装和升级窗口）照哪套规范做，由产品线定，顶层会话维护规范；这取代 ADR 0017 里「统一设计归品牌负责人牵头」中关于应用界面的部分。
- 品牌一侧照旧负责官网、logo、应用图标、吉祥物原稿和对外文案；应用里用这些素材时只拷贝使用，不在各项目里改图。
- 原因：应用的界面跟着产品方向走（界面分桌面小精灵、首页、工作台三层），和产品取舍分不开，放在同一侧改得快。
