# 0007 提示词放成文件：每个配件一个 `prompts/`，顶层一页总览

状态：有效。取代 0019（提示词改动怎么审，照 0027 改过的写）。

## 决定

1. **每个用到模型的配件，提示词放在 `prompts/` 里**：放在仓库根目录；Python 配件也可以放在包目录里（例如 `luoke_mem/prompts/`），随包装进安装包。
2. **每个任务一组纯文本文件**：
   - `<任务>.system.txt`：固定说明；
   - `<任务>.user.txt`：每次输入的措辞和顺序；
   - `<任务>.schema.json`：输出格式；
   - 有重试的加 `<任务>.retry.txt`（答错后补的纠正话），仓库里有共用句子的加 `_shared.txt`。

   用 `.txt` 和 `.json`，不用 `.md`：出版判断配件有没有改动时排除 `*.md` 和 `docs/`，这些文件改了算配件有改动。
3. **代码不写提示词**：只负责读文件、取字段、截短、填占位符、发请求和解析。拼一行输入时用的连接字（编号、截短标记这类）和取字段分不开的，可以留在代码里，在组件的 DESIGN 里写明。
4. **占位符严格核对**：要填的没填、填了的不在文件里，加载时就报错。枚举（类别、动作、话题列表）只写在 `schema.json` 里，提示词用占位符引用。配方里的开关写成可选段 `{{#名字}}…{{/名字}}`，值为空时整段不要，开关逻辑留在代码。
5. **顶层一页总览**：系统文档的「任务与提示词」页从各配件的 `prompts/` 生成，有全文、占位符说明、用在哪几档、评测集和最近的分数。
6. **出版证据记提示词指纹**：每个任务的评测证据带 `prompt_sha256`，版本对照标出哪些任务的提示词变了。配件有改动就重评。
7. **每个用到模型的任务都要有评测集**，没有的补上（邮件助手的起草回复、订阅阅读、精选挑选）。新配件一开始就照这个格式写。
8. **改了 `prompts/` 的 PR**：附评测结果；安全相关的提示词（分拣的风险判断、放行这类）附改动前后三档的逐题对比（例如每题的 `suspicious`、`risks`、`cleared`），只看总分不算数。不再要求另一位成员审；这一版能不能带着它发，由品控在发版时看评测定。合并照团队内部的工作约定（改提示词算不可逆，等项目负责人同意）。

## 为什么

- 提示词散在代码常量和 f-string 里，和解析逻辑混在一起，要人工精修得先读懂代码；枚举两处手抄，改漏了不报错。
- 放在各配件自己的仓库，而不是一个统一仓库：提示词和读它的代码、它的评测集同进同出，出版的改动判断和「每个配件版本都要验证」（luoke-core ADR 0008）照常生效，负责人管得到自己的提示词，也守住「提示词在配件里，数值在配方里」（luoke-core ADR 0005）。「一个地方找」由总览页给。
- 逐题对比：一个只改了摘要那一行的 PR，让 128 GB 档的模型对一道钓鱼题少报了一项风险，代码随即把它放行了；分数表几乎看不出来，逐题对比才发现。
