# 0021 完全磁盘访问授权给螺壳本身

状态：已定（2026-11-02）。代码还没改：现在授权的仍是「螺壳体检.app」。

## 背景

体检要读全盘，原来的约定是用户把完全磁盘访问给体检，主控起它时让系统把它记在体检自己名下。深度搜索也要这个权限，这样用户要给两次，主控还要逐个程序判断记在谁名下。

主控的 Python 要解析本账户任何进程发来的 socket 请求，开着本机端点时还收 TCP。系统按「负责的进程」认权限，主控、引擎和工作进程现在都记在螺壳名下，所以授权给螺壳时，这些进程不能跟着拿到权限。

## 决定

- **用户只授权一次**：完全磁盘访问给螺壳本身，体检、深度搜索复用这一份。
- **主控脱离**：Swift 本体起主控时 disclaim 一次，主控、引擎、工作进程和不要权限的空闲任务都脱离，不用逐个判断。
- **要读全盘的程序由本体起**：本体核过声明和签名后起，不 disclaim。排期留在主控的 `jobs`，主控告诉本体该跑了；参数、环境、SIGTERM 后 15 秒 SIGKILL、异常重启、卸载时停，都和现在的配件规矩一样，退出码和 stderr 交回主控记账。
- **按程序声明**：配件清单里 `jobs` 的项和常驻项各写 `"permissions": ["fda"]`，不要权限的不写（比如体检的 `update`）。`"owner": "luoke"` 只管权限页怎么列。
- **状态由本体报**：只有持权限的进程探测得到。权限页以本体报的为准，配件探到什么照实报。
- **请求授权的卡片要等这几件做完才出**：主控起 `jobs` 前核签名和版本；退回不支持这套做法的旧版时怎么处理；在测试机上手动授权实测一次，包括升级和退出螺壳时，正在跑的程序还算不算有授权。

## 后果

- 持权限的只有本体和声明过的程序，「默认不给」由结构保证。代价是本体要接管这部分进程管理。
- 常驻的 `luoke-audit-serve` 这类程序由本体起，也跟着本体，它和读全盘之间不再有系统隔开。邮件里的注入经 agent 到 serve 这条路，只剩用户点按一道：serve 仍不带碰文件的代码，会改动东西的调用只认用户点按。
- 主控记到裸的 python3 名下，以前算在螺壳名下的权限弹窗会变，要测。
- `disclaim` 用的是私有接口（`responsibility_spawnattrs_setdisclaim`），Python 的 `subprocess` 和 Swift 的 `Process` 都传不了，要自己调 `posix_spawn`。
- 主控 DESIGN §10 和体检、agent、深度搜索的注册页要跟着改。ADR 0013 不变：这是进程之间的防护，不是组件之间的隐私限制。

## 修订（2026-11-06，权限由螺壳统一去要）

主人 11-06 早会定了敏感权限的请求流程（luoke-ops#98）。主人原话：

> 权限流程：组件向螺壳 app 请求权限，用户同意后，螺壳 app 检查自己权限，没有的话向操作系统请求权限；scan 这类需要敏感权限的，安装完后让螺壳 app 启动一下自己，在用户还有意识的时候把权限请求到，避免突然弹窗请求敏感权限的情况

- **组件不直接向系统要权限**：组件向螺壳请求，用户同意后，螺壳先查自己有没有，没有再向系统要。系统那一层的授权给的是螺壳本身，和本 ADR 的「用户只授权一次」一致。
- **敏感权限装好就要**：螺壳扫描这类要敏感权限的，装好（在「应用」里开启）以后由螺壳拉起一次，趁用户正在操作、知道为什么，把权限要到；不在跑的时候突然弹窗。

当时的现状（internal-1106，luoke-ops#87）：

- 由螺壳起的螺壳扫描用上了螺壳的完全磁盘访问。起螺壳里的程序时都没有 disclaim，起之前只核扫描的签名和版本，搜索、邮件助手、agent 核心不核。
- 本 ADR 的「主控脱离」还没做，所以主控的 Python、引擎和空闲任务也跟着有这个权限。上面的流程改的是怎么要，这一点不变。

还没定的：

- 本 ADR 哪几条跟着改、授权卡片跟不跟 beta 2，由 johnz 定（luoke-ops#98、#55）。
- disclaim 挡不挡得住，由 Keith 测了回 #55。Keith 在早会帖里提了第一次真用到时再请用户确认一次（像浏览器里网页要摄像头），也一起定。

## 修订（2026-11-06，现状补记）

这一节不是新决定，只补上一条修订没写到的现状和过时的地方。

**过时的地方**

- 开头「现在授权的仍是螺壳体检.app」过时了：现在授权的就是螺壳本身。
- 名字：体检现在叫螺壳扫描，深度搜索现在叫螺壳搜索，都打在螺壳.app 里（ADR 0022）。
- 「后果」里 `luoke-audit-serve` 那一条过时了：这个程序没有了，扫描不常驻，要用时由本体起。

**和原文做法不同的地方**

- **起程序时不看清单**：本体要起什么写死在本体里。扫描的清单写了 `"permissions": ["fda"]` 和 `"owner": "luoke"`，权限页读这些声明，本体和主控起程序时不读。
- **空闲任务**：不是「主控告诉本体」，而是主控起螺壳的 `--run-tool` 模式，由这个进程核过再起工具。排期、SIGTERM 后 15 秒 SIGKILL、退出码和 stderr 记账，和原文一样。
- **状态由本体报**：接口有了，本体还没报，现在是扫描自己探测。
- **请求授权的卡片**：原文要等三件做完才出，卡片已经在内部版里出了。这三件的现状：
  - 主控起 `jobs` 前核签名和版本：只有扫描做了。
  - 退回不支持这套做法的旧版时怎么处理：没定。
  - 手动授权实测：扫描在正式签名的内部版上用上了这份权限。搜索没测，升级时和退出螺壳时也没测。
- **文档**：主控 DESIGN §10 没改，扫描的注册页还是旧内容（`projects/luoke-audit.md`）。

**「主控脱离」结论待定**

等真签名测试出来再下结论，两种结果的走向：

- **disclaim 挡得住**：照原决定做。主控要自己调 `posix_spawn` 起，`--run-tool` 脱离以后还算不算螺壳也要测。
- **disclaim 挡不住**：「主控脱离」和「默认不给由结构保证」都不成立，要另定怎么把主控和这份权限分开，到时再写修订。

## 修订（2026-11-06，确认一次、只在用户操作后弹）

johnz 11-06 定（luoke-ops#100，接主人早会定的流程和 Keith 的两步设计）：

- **只确认一次**：用户在「应用」里开启组件时确认它要的权限，不再在第一次用到时单独弹第二个框。开启后马上发起第一次检查，让第一次真用到紧跟着用户的操作。
- **关掉了才再问**：用户后来手动关掉了它的权限，下次要用时再请求。
- **都要声明**：组件要用的权限都在清单里声明，没声明的不能申请。
- **不静默弹窗**：所有授权请求都在用户操作之后马上弹出，让用户知道这次授权和自己刚做的事有关。
- **看得到**：权限页列出每个组件确认过什么。

disclaim 的测试仍由 Keith 做，结论回 luoke-ops#55。
