# 0009 产品线和发版品控分开：品控按版本做，不按 PR 做

状态：有效。取代 0027。负责人的细目、谁能合什么、会话之间怎么往来，只写在团队内部的工作约定里；这里写怎么分、为什么。

## 决定

1. **产品线归一处**：螺壳 app 的产品代码（主控的产品部分、agent、探头（浏览器插件）、输入法、邮件、记忆，以及螺壳搜索、螺壳扫描的界面）由项目负责人这边迭代；产品上的事（做什么、界面、取舍、哪个改动进哪一版）由项目负责人定，第 2 条里归发版品控一侧的两样后端除外。
2. **所有应用是同一个架构**：和界面、用户交互有关的部分都在 luoke-agent（0002），由项目负责人直接负责；各应用的业务逻辑（后端）由原来的负责人维护。邮件、记忆、输入法的后端在产品线，螺壳搜索、螺壳扫描的后端各归发版品控的一位负责人，是同一种安排。
   - 后端做什么、怎么做由负责的一方定：螺壳扫描的后端和命令行、螺壳搜索的后端，各由它的负责人定。产品线对后端有需求，在后端的仓库提 issue。
   - 这两样后端由各自的负责人自己排期、直接定，普通的后端改动自己合，不用另一位同意。设计上要和别的仓库协同的（改或删 MCP 工具、outbox、资源、主控任务、配件清单这些对外接口），要另一个人一起定：算不算协同不靠作者自己标，由仓库里的 CI 或负责协调的一方扫 PR 判断，判出来了由它指定另一个人。这两个仓库里的 `.github/workflows` 和安全相关的改动（第 5 条），要发版品控的两位负责人里作者以外的那一位 Approve，并且落在合并的那个提交上。
   - 这两样的界面归 luoke-agent，和 luoke-core 一起做；发版品控一侧不管界面。
3. **发版和品控一条线，由两位负责人管**：出版流水线、截版和发布、公开同步、评测程序和评测集、配方的验证、配件发布的 CI（配件能不能发由它把关，主控不再按版本认配件，见 0008 第 18、19 条）。这一版能不能发，由他们看评测和 CI 的结果定。
4. **品控按版本做，不按 PR 做**：产品仓库的 PR 不要求作者以外的人逐个审；品控在发版时把关，没过就报哪一项没过、卡在哪个提交，只报事实，怎么修由产品这边定。
5. **发版品控一侧另外负责的**，是「产品代码归产品线」的例外：
   - 安全相关的改动（安全审查提出的修复、本机数据加密、签名和授权的核对、权限边界、读不可信输入时的加固；按事情算，不按目录）；
   - 各产品仓库的 CI 配置（`.github/workflows`）；
   - 主控仓库里出版和评测的目录（仓库本身归产品线）；
   - 螺壳搜索、螺壳扫描的后端。

   产品会话不改这几样，要改提 issue。
6. **科研单独做**：推理引擎（0003）、专用的垂直小模型由发版品控的两位负责人做实验，结论报给项目负责人；要不要用进产品由项目负责人定。
7. **品牌和外部趋势**：品牌的负责人看外面 Local AI 的讨论趋势，和项目负责人一起做品牌；官网、文案、社区照 0008。
8. **两条线之间只留三样往来**：产品这边交版本，品控回结果，科研和趋势报进展。

## 取舍

- 逐个 PR 的审核能更早发现问题，但每个改动都要等人；按版本把关发现得晚一些，靠评测和 CI 的覆盖面补。评测和 CI 核什么由品控这条线定，并随发现的问题补。
- 各产品原来各有负责人、各是独立的应用；合成一个应用以后，每个应用还留着自己的页面流程，改一处界面要交叉问几个人、等别人同意，开发又慢又乱。界面收到一处，后端留给懂它的人。
- 应用的界面跟着产品方向走，和产品取舍分不开，放在同一侧改得快。
